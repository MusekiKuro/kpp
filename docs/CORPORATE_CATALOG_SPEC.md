# Nurset: техническое задание корпоративного сайта-каталога

Версия: 1.0
Дата: 2026-07-22
Статус: согласованная основа для реализации

## 1. Цель продукта

Расширить существующий лендинг-каталог Nurset до полноценного двуязычного корпоративного сайта-каталога. Посетитель должен быстро найти товар, изучить характеристики, добавить один или несколько товаров в запрос и отправить заявку на коммерческое предложение. Онлайн-оплата на этом этапе не используется.

Сайт должен одновременно решать четыре задачи:

1. Представлять компанию и ассортимент.
2. Привлекать органический поисковый трафик на категории и товары.
3. Собирать качественные заявки на коммерческое предложение.
4. Позволять администратору и автоматизированному агенту безопасно наполнять каталог.

## 2. Зафиксированные решения

- Текущий стек сохраняется: Next.js 16 App Router, React 19, Supabase, Tailwind CSS 4.
- Публичная часть работает на русском и казахском языках.
- Административная панель может оставаться только на русском языке.
- Онлайн-оплата, эквайринг и оформление доставки не входят в MVP.
- Цена нового товара по умолчанию отображается как «По запросу».
- Администратор может включить точную цену или цену «от» для отдельного товара.
- Раздел «Услуги» в MVP не создаётся.
- Товары добавляются вручную, из Excel/CSV и из нормализованного JSON, подготовленного ИИ-агентом из текста.
- Массовый импорт никогда не публикует товары напрямую: сначала проверка, затем предпросмотр и подтверждение человеком.
- Русский контент обязателен для публикации русской версии.
- Казахский контент может быть создан ИИ как черновик, но должен иметь отдельный статус проверки.
- Существующая защищённая SSR-аутентификация Supabase и роль `app_metadata.role = admin` сохраняются.

## 3. Границы MVP

### 3.1 Входит в MVP

- двуязычная публичная часть RU/KZ;
- главная страница корпоративного сайта;
- дерево категорий и подкатегорий;
- каталог с поиском, фильтрами, сортировкой и пагинацией;
- страницы категорий, брендов и товаров;
- несколько изображений товара;
- структурированные характеристики;
- четыре режима отображения цены;
- запрос коммерческого предложения вместо классической покупки;
- страницы «О компании», «Доставка и гарантия», «Контакты»;
- административное управление товарами, категориями, брендами, изображениями, переводами и ценами;
- административный просмотр и обработка заявок;
- безопасный импорт Excel/CSV/JSON;
- контракт для ИИ-агента, преобразующего текст или таблицу в импортный JSON;
- черновики, предпросмотр и публикация;
- базовое SEO, sitemap, robots, canonical и hreflang;
- базовая аналитика заявок и UTM-меток;
- аудит импортов и административных изменений, влияющих на каталог.

### 3.2 Не входит в MVP

- онлайн-оплата;
- личный кабинет покупателя;
- складской учёт в реальном времени;
- интеграция с 1С;
- автоматическое формирование счетов и накладных;
- бонусы, промокоды и программы лояльности;
- отзывы и рейтинги;
- полноценный раздел услуг;
- блог/новости;
- встроенная LLM-интеграция с оплатой токенов;
- автоматическое скачивание изображений с сайтов без подтверждённых прав использования;
- автоматическая публикация переводов или импортированных товаров.

## 4. Пользователи и роли

### 4.1 Посетитель

Может:

- выбрать RU или KZ;
- просматривать опубликованные категории, бренды и товары;
- искать и фильтровать товары;
- видеть цену согласно режиму товара;
- добавлять товары в список запроса;
- менять количество;
- отправлять заявку на коммерческое предложение;
- переходить в WhatsApp или звонить;
- читать корпоративные страницы.

Не может:

- видеть черновики;
- изменять каталог;
- видеть заявки других пользователей;
- обращаться напрямую к административным операциям Supabase.

### 4.2 Администратор/контент-менеджер

Авторизуется через Supabase Auth и считается администратором только при `app_metadata.role = admin`.

Может:

- создавать и редактировать каталог;
- управлять RU/KZ-контентом;
- назначать режим и значение цены;
- загружать и сортировать изображения;
- создавать черновик и публиковать локализованную версию;
- запускать импорт и подтверждать изменения;
- просматривать заявки и менять статусы;
- видеть ошибки качества данных и импорта.

### 4.3 ИИ-агент импорта

ИИ-агент не получает прямого доступа к production Supabase и не использует `service_role` ключ.

Его задача:

- прочитать Excel/CSV или предоставленный текст;
- привести данные к опубликованному JSON-контракту;
- указать источники и предупреждения;
- выполнить локальную dry-run проверку;
- передать файл администратору или административному endpoint для staging;
- не применять импорт без явного подтверждения человека.

- логотип;
- каталог;

## 7. Главная страница

Главная должна состоять из управляемых или переиспользуемых блоков:

1. Hero с корпоративным позиционированием и CTA «Перейти в каталог».
2. Основные категории.
3. Популярные или рекомендуемые товары (`is_featured`).
4. Преимущества компании без неподтверждённых маркетинговых утверждений.
5. Краткий блок «О компании».
6. Контакты/филиалы.
7. CTA «Получить коммерческое предложение».

Контент, который требует юридического или фактического подтверждения, не выдумывается агентом.

## 8. Каталог

### 8.1 Категории

- категории образуют дерево через `parent_id`;
- глубина MVP: до трёх уровней;
- каждая категория имеет общий ASCII slug, RU/KZ-названия, RU/KZ-описания, SEO-поля, порядок и статус;
- категория может определять доступные фильтры и характеристики;
- пустые или выключенные категории не должны создавать индексируемые пустые страницы.

### 8.2 Поиск и фильтрация

Минимальные фильтры:

- категория/подкатегория;
- бренд;
- наличие;
- режим цены;
- диапазон цены для товаров с числовой ценой;
- динамические характеристики, отмеченные `is_filterable`.

Сортировка:

- по рекомендуемому порядку;
- по названию;
- сначала новые;
- цена по возрастанию/убыванию только для числовых цен.

Поиск работает по текущей локали, SKU и бренду. Фильтры и пагинация отражаются в query string и доступны по прямой ссылке.

### 8.3 Пагинация и производительность

- серверная пагинация;
- размер страницы по умолчанию 24;
- максимальный размер ответа ограничен;
- публичная страница не получает весь каталог одним JSON;
- запросы выбирают только нужные поля;
- после изменений в админке инвалидируется catalog cache/tag;
- изображения получают корректные `sizes`, lazy loading и фиксированное соотношение сторон.

## 9. Страница товара

Обязательные элементы:

- breadcrumbs;
- главное изображение и галерея;
- название на текущем языке;
- бренд;
- SKU;
- статус наличия;
- режим/значение цены;
- краткое описание;
- таблица характеристик;
- полное описание;
- гарантия и документы, если заполнены;
- кнопка «Добавить в запрос»;
- CTA WhatsApp;
- похожие товары из той же категории;
- локализованные metadata и JSON-LD Product без ложных offer-данных.

Если KZ-версия не опубликована, URL не должен отдавать русскую страницу как полноценную KZ-страницу. Допустимо показать 404/redirect по согласованной политике; для MVP рекомендуется скрывать непроверенную KZ-версию из выдачи и sitemap.

## 10. Цена и наличие

Режимы цены:

```text
request  -> «По запросу» / «Сұрау бойынша»
exact    -> точная цена
from     -> «от {price} ₸»
hidden   -> ценовой блок скрыт, CTA запроса остаётся
```

Поля:

```text
price_mode
price_amount
old_price_amount
currency = KZT
```

Правила:

- `request` является значением по умолчанию;
- `exact` и `from` требуют положительный `price_amount`;
- `request` и `hidden` могут иметь `price_amount = null`;
- старая цена не может быть меньше или равна текущей, если отображается как скидка;
- отсутствие онлайн-оплаты должно быть очевидно: цена не создаёт кнопку «Купить»;
- наличие MVP: `unknown`, `in_stock`, `on_order`, `out_of_stock`.

## 11. Запрос коммерческого предложения

Термин в публичном UI: «Запрос» или «Получить коммерческое предложение», а не «Покупка».

### 11.1 Список запроса

- хранится локально до отправки;
- содержит product ID и количество;
- сервер заново загружает актуальные данные товаров;
- пользователь не может подменить название, SKU, изображение или цену;
- удалённый/неопубликованный товар вызывает понятное предупреждение.

### 11.2 Форма

Поля:

- имя — обязательно;
- телефон — обязательно;
- email — необязательно, но валидируется;
- организация — необязательно;
- БИН — необязательно;
- город — необязательно;
- комментарий — необязательно;
- язык заявки;
- согласие на обработку персональных данных — обязательно;
- скрытые source URL и UTM-метки.

### 11.3 Хранение заявки

Рекомендуется отделить запрос КП от будущих ecommerce-заказов:

```text
quote_requests
quote_request_items
```

Заявка хранит snapshot SKU/названия/режима цены на момент отправки. Товар может быть позже удалён, но историческая заявка остаётся читаемой.

Статусы MVP:

```text
new
contacted
in_progress
closed
rejected
```

Публичный пользователь не получает прямой `INSERT` в таблицы Supabase. Публичный Next.js route валидирует, ограничивает частоту и вставляет данные через строго серверный механизм. `service_role` никогда не попадает в client bundle.


## 13. Миграционная стратегия

1. Создать резервную копию и проверить текущую миграцию безопасности.
2. Добавить новые таблицы и nullable-поля без удаления старых.
3. Создать категории и бренды из уникальных legacy-строк.
4. Заполнить `name_ru`, `description_ru`, `category_id`, `slug` из legacy-полей.
5. Оставить товары без SKU в статусе review.
6. Перевести чтение публичного сайта на новые поля с временным fallback.
7. Перевести админку на новые API.
8. После smoke test отключить запись legacy-полей.
9. Удаление legacy-полей — отдельная будущая миграция и отдельное подтверждение.

Любая миграция production требует human review и сначала выполняется на тестовом проекте Supabase.

## 14. Импорт и дальнейшая автоматизация

### 14.1 Каналы

- XLSX;
- CSV UTF-8;
- нормализованный JSON;
- текст, который внешний ИИ-агент преобразует в JSON.

### 14.2 Процесс

```text
Источник
  -> parser
  -> нормализация
  -> JSON Schema validation
  -> staging/import_rows
  -> сопоставление SKU/external_id
  -> preview diff
  -> human approval
  -> transactional apply
  -> audit report
```

### 14.3 Правила

- основной ключ сопоставления — SKU;
- `external_id` используется только в пределах известного источника;
- совпадение по названию не должно автоматически обновлять товар;
- отсутствие SKU создаёт ошибку или черновик review, но не опубликованный товар;
- повторная загрузка того же файла определяется по hash;
- операция apply идемпотентна;
- импорт не удаляет товары автоматически;
- очистка отсутствующих строк выполняется только отдельной операцией с подтверждением;
- импорт изображения использует разрешённый источник и переносит файл в Supabase Storage после проверки;
- RU/KZ-поля импортируются отдельно;
- AI-перевод маркируется `ai_draft`;
- каждая строка показывает create/update/skip/error и diff полей.

### 14.4 XLSX parser

В проекте сейчас нет production-зависимости для XLSX. Перед добавлением библиотеки агент должен подтвердить выбор поддерживаемого пакета, его лицензию, browser/server runtime и ограничения безопасности. Старые ad-hoc Python/ZIP-скрипты не считаются production importer.

### 14.5 Контракт ИИ-агента

В репозитории должен появиться документ и JSON Schema с точным форматом входа. ИИ-агент:

- не придумывает SKU, цену, гарантию и технические характеристики;
- неизвестные значения оставляет `null` и добавляет warning;
- хранит исходный фрагмент/номер строки;
- не скачивает изображения без разрешения;
- не применяет данные напрямую к БД;
- всегда сначала запускает dry-run.

## 15. Административная панель

### 15.1 Товары

- таблица с серверной пагинацией;
- поиск по SKU, RU/KZ-названию;
- фильтры категории, бренда, публикации, цены, перевода, изображения;
- создание/редактирование;
- отдельные вкладки RU и KZ;
- price mode и цена;
- структурированные характеристики;
- галерея с сортировкой и primary image;
- preview RU/KZ;
- publish/unpublish отдельно по локали;
- архивирование вместо необратимого удаления по умолчанию;
- предупреждения «нет SKU», «нет KZ», «нет изображения».

### 15.2 Категории и бренды

- CRUD;
- дерево категорий;
- защита от циклов `parent_id`;
- уникальные slug;
- запрет удаления сущности, используемой опубликованными товарами, без явной стратегии переноса;

## 16. API и серверные контракты

Публичные операции:

- read-only published catalog;
- отправка quote request;
- поиск и фильтрация только по разрешённым параметрам.

Административные операции:

- CRUD categories/brands/products/attributes;
- gallery upload/reorder/delete;
- publish/unpublish;
- import upload/validate/approve/apply;
- quote request status update.

Требования:

- строгий allowlist полей;
- ограничение размера body и файла;
- UUID/slug/enum validation;
- безопасные ошибки без внутренних деталей;
- `res.ok` проверяется клиентом;
- административные endpoints вызывают `requireAdmin`;
- RLS повторяет серверные права;
- никакие server secrets не экспортируются через `NEXT_PUBLIC_*`;
- публичные ответы не включают draft/private/import fields;
- rate limiting production дублируется на платформе.

## 17. Безопасность и обязательный incident gate

В tracked-скриптах `list_products.js` и `update_images.js` обнаружен захардкоженный Supabase privileged key. Он считается скомпрометированным.

До продолжения feature development необходимо:

1. Отозвать/перевыпустить ключ в Supabase вручную.
2. Удалить значение из tracked-файлов и использовать только server env.
3. Не переносить значение в `.env.example` или документацию.
4. Если репозиторий когда-либо отправлялся на remote, проверить и очистить историю отдельной согласованной процедурой.
5. Проверить логи Supabase на подозрительные операции.
6. Не запускать старые скрипты до ротации.

Дополнительно:

- не доверять `user_metadata`;
- cookies и refresh выполняются через `@supabase/ssr`;
- KZ/RU-текст рендерится как текст, не как произвольный HTML;
- XLSX/CSV считаются недоверенным вводом;
- CSV export защищён от formula injection;
- изображения проверяются по MIME, magic bytes, размеру и допустимому формату;
- external URL не делает сайт универсальным image proxy;
- персональные данные заявок видят только администраторы;
- privacy consent хранится с timestamp.
